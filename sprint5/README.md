# Sprint 5 - 系统整合、测试与交付优化

**时间范围**：第 5 个迭代周期（1 周）
**Sprint Goal**：完成 `web-console`、`backend-core`、`ai-service` 和 `device-simulator` 的全面联调，修复离线、缓存、AI 多动作、设备冲突等关键缺陷，并整理可演示、可验收的交付版本。

## 1. 背景与范围

前四个 Sprint 已完成基础架构、设备控制、发现绑定、缓存和场景/AI 能力。本 Sprint 重点是整合、测试、缺陷修复和交付文档校准，不新增真实用户认证、生产数据库、WebSocket 推送或移动端 App。

## 7. 依赖关系

- AI 多动作验收依赖至少两台同类型设备已绑定，例如 `ac-003` 与 `ac-004`。
- C++ 编译在 Windows 下依赖 MSYS2 或可用 POSIX 头文件环境。
- 无外部 API key 时应验证 mock 或本地降级路径。

## 8. Acceptance Criteria

- 按文档启动四个模块后，Web 控制台可完成设备发现、绑定、控制、移除。
- 已绑定设备刷新后恢复；模拟器关闭后显示离线，不允许控制。
- 同 ID 异类型设备显示冲突，后端拒绝命令，场景不可用或执行失败。
- 用户可创建、执行、删除自定义场景；预设场景仍保留。
- 自然语言可解析基础设备控制、多动作控制和自然语言场景创建。

## 9. Definition of Done

- 候选设备不常驻主页，只在添加家电弹窗展示。
- 前端不展示无法真实控制的在线状态。
- 后端命令执行前经过绑定、类型、能力和在线状态检查。
- AI 输出不直接执行，必须通过后端动作校验。
- 文档中的功能范围、启动步骤和验收方式与本阶段交付版本保持一致。

## 10. 测试与验收方案

- 前端：`node --check smart-home-system/web-console/app.js`。
- 后端：`python -m py_compile backend-core/app/services/home_orchestrator.py`，环境具备时运行 pytest。
- AI：`pytest ai-service/tests -v`，手动调用 `/internal/v1/nlu/interpret` 验证多动作。
- C++：`cmake --build smart-home-system/device-simulator/build`。
- 集成：启动并绑定 `ac-003`、`ac-004` 后输入“同步打开全部空调”。

## 11. Sprint Review 预期成果

- 演示完整启动顺序和健康检查。
- 演示从空家庭到发现、绑定、控制、缓存恢复。
- 演示场景创建、自然语言场景和场景执行。
- 演示两台空调批量自然语言控制。
- 展示测试命令和已知限制。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 外部模型服务不可用 | AI 链路失败 | NLU 规则优先，ASR/TTS 提供 mock 或本地降级。 |
| 本地缓存污染演示 | 页面显示旧设备 | 演示前检查或备份 `home_state.json`。 |
| 模拟器进程与缓存不一致 | 用户误操作 | 离线/冲突状态和后端二次校验作为防线。 |
| 文档与演示流程不同步 | 验收时产生误解 | Sprint 文档、启动说明和演示脚本保持同一套口径。 |

## 13. Sprint Retrospective

本 Sprint 的核心价值是让系统从“功能可以跑”变为“演示可控、边界清楚、错误可解释”。本阶段重点完成课程交付所需的集成、测试、说明文档和演示流程整理。
